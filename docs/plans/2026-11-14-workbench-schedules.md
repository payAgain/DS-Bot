# Scheduled tasks in the workbench

User-authorized integration of existing schedules into the persistent task workbench. Host schedules remain the only scheduler; no schedule is copied into `bot/tasks.json` and no timer is created by the workbench.

- Read exactly the same team-scoped catalog as the existing DS Bot scheduled-task settings page. Tasks outside that existing user-visible scope remain excluded. Bot schedule tools and their own-chat restrictions are unchanged.
- The board distinguishes scheduled tasks in their own section with enabled, awaiting delivery, paused, finished or unknown state. These are not ordinary todo tasks. The type filter selects ordinary or scheduled tasks; personal/Bot filters continue to apply to ordinary tasks.
- Project only each active task's currently committed future `scheduledAt` into the visible 42-day month grid. This is an instant, not occupied work time. Do not enumerate the recurrence. Suppress paused/ended/invalid/overdue future events and clearly disclose the next-only coverage. Viewing-zone conversion uses the same task calendar helpers; rule zones come from timeZone or DTSTART TZID, otherwise UTC.
- Details show the real instruction as plain text, rule, owner, next delivery and saved latest delivery receipt. A receipt acknowledges inbox delivery, not successful model completion; executionActive only means queued/running when the Host provides it.
- Reuse public `schedule.catalog()` and `schedule.edit()` APIs. The new authenticated user endpoint is restricted to already-visible tasks and permits title/prompt, existing RRULE editing, pause/resume and delete with required `expectedUpdatedAt` (including null for absent legacy revisions). Keep target unchanged. Native schedule_conflict and not-found results are not converted to success.
- There is also an explicit link to the existing DS Bot schedule manager and original conversation. No new run-now control or automatic execution is introduced. Non-RRULE timing remains managed through existing Host/Bot tools; this panel edits its name/instruction and lifecycle.
- Guard task draft and schedule edit drafts from accidental navigation. Re-fetch after writes and discard reads from before a successful edit, so an older poll cannot undo the current display. No automatic retries of a mutation.

Verification uses isolated schedule-service fixtures for reads, visibility, conflict, control payloads, refresh and time boundaries. Production acceptance is read-only: record stable hashes of the visible schedule collection/config/status/rrule/target before and after, never toggle or create a real schedule for testing. Inspect actual rendered UI at the original URL without a replacement server. Rollback to .14 preserves both the ordinary task store and all Host schedules.

SDK reference: https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/schedule/schedule/README.md (catalog, edit, expectedUpdatedAt); local installed public declarations of @deepseek-ai/dsh-schedule at 0.2.2-rc.1 are the version-specific contract.
